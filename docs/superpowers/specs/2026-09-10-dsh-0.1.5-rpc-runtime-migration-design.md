# DSH 0.1.5 RPC and Runtime Migration Design

## Objective

Migrate the IntelliJ integration from `deepseek-harness` `dsh-v0.1.2-rc.1` to `dsh-v0.1.5-rc.1` at commit `183f08e9c6dde7e36cd2318eaee70b0da08fb35e`. The migration covers the complete protocol and Runtime lifecycle behavior implemented by `dsh-ide` v0.9.2, translated to IntelliJ Platform APIs rather than copied mechanically from VS Code.

The plugin will support one protocol version at a time. It will not mix compatibility branches for retired Remote protocols into the current state machine, and it will not rewrite, downgrade, move, or delete user Session data.

## Source of Truth and Scope

The protocol authority is the `dsh-v0.1.5-rc.1` source under `../dsh-ide/deepseek-harness/`. The reference client behavior is commit `48571ec` in `../dsh-ide`, which introduced the 0.1.5 migration. The later `dsh-ide` commit that excludes internal RPC documents from its VSIX does not change Runtime behavior.

The migration includes:

- the Remote endpoint audit and Runtime version pin;
- transient Assistant streaming and durable settlement reconciliation;
- V3 Session history field normalization and projection behavior;
- Goal activation events and paused/resume presentation;
- command attachment and subagent prompt argument changes;
- newly relevant System and PTC events in chat and Trace projections;
- removal of the temporary September 10 model injection;
- compatible local Runtime discovery, managed and package-manager fallbacks;
- shared Runtime lock versioning, ownership, legacy-instance migration, and safe reclamation;
- cancellation-safe startup, idempotent shutdown, and owned process-tree termination;
- English and Chinese settings and Runtime documentation.

VS Code-only UI mechanics are excluded. Their observable behavior will use IntelliJ notifications, dialogs, services, executors, and process APIs. Features absent from the existing IntelliJ product surface, such as the VS Code Web Sidebar and file-upload UI, will not be added solely because they exist in the reference client.

## Architecture

`DshRuntimeService` remains the stable Runtime facade consumed by the plugin. Protocol and lifecycle concerns move into focused collaborators so the facade does not absorb another independent state machine:

- `DshRuntimeLock` reads, validates, serializes mutations to, and conditionally removes the shared `dsh-runtime.lock` record.
- `DshRuntimeMigration` inspects an incompatible or unversioned lock, proves whether a candidate is an orphaned DSH Runtime, requests explicit user confirmation, and revalidates identity before termination.
- `DshRuntimeProcess` starts an owned Runtime, records process ownership evidence, terminates its process tree, and reports when descendant ownership cannot be proven.
- `DshAssistantStream` validates the 0.1.5 opening baseline and incremental `start`, `chunk`, and `end` frames, while reconciling them with durable `assistant/message` and `assistant/attempt` events.
- `DshRemoteContracts` remains the only endpoint and request-envelope authority.
- `DshRemoteConnection` owns connection generations and logical follow streams.
- `DshRemoteState` owns durable Session, workspace, catalog, control, and transient Assistant presentation state.
- Existing message and Trace projectors consume normalized state and never interpret mux envelopes or lock records.

No Node sidecar or upstream Cordis client runtime will be embedded. That would add a second runtime, IPC protocol, packaging surface, and failure domain without removing the existing Java state model.

## Remote Protocol Changes

### Version and carrier

`DshRemoteContracts.TARGET_TAG`, `TARGET_COMMIT`, settings defaults, package-manager arguments, managed Runtime version, diagnostics, README tables, and localized protocol notes will all identify `0.1.5-rc.1`. HTTP unary envelopes, `/api/<namespace>/<method>`, `/api/remote.mux`, `$events`, and `$events/result` remain unchanged.

The plugin will reject a local Runtime whose exact version is not `0.1.5-rc.1`. A user-configured external server remains connect-only, but its Remote capability must still pass the existing RPC compatibility probe before the plugin marks it running.

### Assistant stream

Every retained `session/follow` request will set `assistantStream: true`. Its first frame must be a `snapshot` containing an `assistantStream` baseline. The baseline and later `assistant-stream` frames are process-local presentation state and never consume or synthesize durable Session sequence numbers.

`DshAssistantStream` enforces:

- dense connection-local revisions;
- one active attempt at a time;
- stable non-empty `attemptId` values;
- continuous chunk indexes;
- valid `startedAfterSeq`, turn, and step values;
- lossless expansion of `chunk`, `text-chunks`, `reasoning-chunks`, and `tool-call-chunks` records;
- durable settlement only through a later matching `assistant/message` or `assistant/attempt` event;
- a committed `end` that refers to the exact settlement sequence and type;
- an abandoned `end` only when no durable settlement exists.

On reconnect or stop, old transient Assistant state is cleared. The next generation adopts only its opening baseline. Message and Trace projectors suppress legacy chunk-derived partials for the same live turn and step, preventing duplicate output.

### Session V3 and projections

The wire decoder accepts replacement operations using `startSeq` and `endSeq`, validates them, and normalizes them to the existing internal range vocabulary. Legacy `start` and `end` fields may be accepted only at the normalization boundary for already retained in-memory or fixture data; newly received 0.1.5 frames use the V3 names.

Durable Assistant events containing compressed `stream` data are validated and expanded before projection. Chat history continues to show append-origin conversation even when model-visible surface replacements remove earlier nodes. `system/message` is projected where it is user-visible, and PTC dispatch start/settlement events are paired by `subCallId` in Trace alongside existing code-dispatch events.

History pagination stays bound to the opening snapshot cursor. Results from a superseded connection generation are discarded. Queue, job, projection, and title baselines are updated together so reconnects cannot combine new catalog state with stale control state.

### Endpoint arguments and events

`commands/execute` sends `agentId`, `line`, and `submittedAttachments`. Each submitted image carries a `type: "image"` discriminant. Command descriptors read `input.attachments` instead of `input.images`.

`subagents/prompt` sends one top-level `request` object containing `parentSessionId`, `childSessionId`, `mode`, `delivery: "queue"`, `requestId`, content, and optional client time zone.

The Remote event allowlist includes `goal/activation-changed`, and event callbacks preserve the forwarded argument array. Goal activation is process-local state tied to an exact goal id and revision. Active goals with `disarmed` activation expose Resume; stale activation events do not modify another goal revision.

The model catalog comes entirely from the Runtime. The temporary `deepseek-v4.1-flash-expires-on-0910` injection and its expiry logic are removed.

## Runtime Discovery and Version Enforcement

The default launcher mode becomes `auto`, with default arguments `web --no-open`. Auto discovery uses this order:

1. an exact-version `dsh` executable from the IntelliJ shell environment or PATH;
2. an exact-version npm-global executable;
3. pinned `pnpm dlx @deepseek-ai/dsh@0.1.5-rc.1`;
4. pinned `npx --yes @deepseek-ai/dsh@0.1.5-rc.1`;
5. a cached or newly installed managed Runtime when its release asset exists.

An explicitly configured launcher remains authoritative and is never silently replaced by auto discovery. Bare package specifications are pinned before launch. An explicitly configured different package version fails compatibility validation rather than being rewritten behind the user's back.

Native and configured launchers are probed with `--version` before ownership is recorded. Package-manager and managed launchers derive the version only from their exact pinned package or managed manifest. All local launch paths must resolve to the same target version.

Discovery and installation observe a startup cancellation token. Disposal, a replacement start, or a switch to an external server cancels pending discovery and prevents late completion from publishing a running state.

## Shared Runtime Lock

The lock filename remains `dsh-runtime.lock` so IntelliJ and VS Code coordinate on one machine-wide Runtime. New records contain:

- advertised `url` and optional `launchUrl`;
- `runtimeVersion`;
- opaque `ownerId`;
- `runtimePid` when a process has been spawned;
- `runtimeProcess` identifying a direct Runtime or wrapper;
- `runtimeProcessGroup` for POSIX owned launches;
- existing editor ownership information needed for compatibility diagnostics.

Lock updates are serialized through a short-lived mutation lock and use file identity plus owner-id checks. An owner removes a lock only after its owned process tree has exited and the advertised loopback endpoint refuses connections. If either condition is uncertain, the lock remains for diagnosis and peers are prevented from starting a second Runtime.

A stale lock whose owner is gone and whose numeric loopback port is closed may be reclaimed. A live compatible Runtime is reused. A live incompatible or unversioned Runtime triggers migration inspection rather than automatic deletion.

## Legacy Runtime Migration

Migration first snapshots the lock contents and identity. It then verifies that the recorded PID and process command represent the DSH npm entry or an owned DSH Runtime, that the editor owner is no longer active, and that the advertised endpoint belongs to the candidate.

If ownership cannot be established, the plugin leaves the process and lock untouched and tells the user to stop the owning editor or inspect the instance. If the Runtime is a provable orphan, the plugin shows a modal confirmation that stopping it interrupts running tasks and may discard unsaved in-flight output while preserving Sessions on disk.

After confirmation, the plugin re-reads the lock and revalidates the process identity. Any change aborts migration. Only then does it terminate the old process tree, wait for process and endpoint shutdown, remove the unchanged lock, and retry discovery with `0.1.5-rc.1`.

## Process Ownership and Shutdown

Owned POSIX launches use a dedicated process group so a package-manager wrapper cannot leave the Runtime descendant behind. Windows launches retain direct-versus-wrapper metadata and use platform process-tree termination only when ownership evidence is sufficient.

Startup publishes PID ownership before waiting for HTTP readiness. A failed attempt terminates its complete owned tree before a fallback registry or launcher is tried. Wrapper exit alone is not evidence that descendants exited.

Start, stop, and dispose share one idempotent cleanup operation. Cleanup cancels discovery and readiness waits, closes Remote streams, terminates the owned process tree within a bounded deadline, verifies endpoint refusal, and releases the lock last. Concurrent calls join the same operation. An uncertain descendant state produces an actionable error and retains the lock.

External Runtime connections are never terminated by this plugin. Switching away from an owned Runtime completes owned cleanup before attaching to the external endpoint.

## Error Handling and User Experience

Protocol errors identify the endpoint and the violated 0.1.5 expectation without exposing tokens, cookies, credentials, prompts, or attachment bodies. Version errors state the detected and required versions. Lock and migration errors include the lock path, PID, and redacted loopback URL when available.

Background work remains off the event-dispatch thread. Migration confirmation and progress notifications return to IntelliJ UI APIs. Cancellation is not reported as a generic launch failure. A Runtime download through a package manager or managed installer reports visible progress and a bounded retry when an alternate registry is available.

The settings UI explains that the version is fixed to `0.1.5-rc.1`; values such as blank or `latest` no longer opt into unaudited protocol versions. Existing persisted `0.1.2-rc.1` defaults are recognized as legacy defaults and migrated to the new auto-launch configuration, while explicit custom launchers remain unchanged.

## Verification

The repository forbids adding unit tests. Verification therefore uses existing checks and isolated integration scripts or commands without adding test sources:

- format and static checks already configured by Gradle;
- Java compilation and IntelliJ plugin verification;
- `git diff --check`;
- isolated Runtime startup with a temporary DSH home and workspace;
- authentication, unary RPC, mux readiness, workspace/session creation, V3 history pagination, title projection, and reconnect smoke checks;
- Assistant `start/chunk/end` streaming with a local loopback model stub, including reconnect recovery and single durable settlement;
- Goal pause/resume activation, command submitted attachments, and subagent queued-delivery argument checks;
- concurrent lock reclamation, cancelled migration, changed-lock rejection, non-DSH PID protection, process-tree shutdown, and startup cancellation checks.

Smoke verification must not read or modify the user's existing Sessions and must not send requests to a paid external model. Managed standalone installation can be reported as unverified if the `v0.1.5-rc.1` release assets remain unavailable; package-manager or existing-instance verification remains required.

## Delivery

Implementation will be divided into reviewable commits for protocol/state migration, Runtime lifecycle migration, and documentation/verification as appropriate. The final repository state will be clean, all applicable checks will pass or have a concrete external limitation recorded, and the completed work will be committed for user review as required by `AGENTS.md`.
